# api/admin/

## Responsibility

Implements the session-authenticated administration API for content management, services, careers/applicants (including ATS results), live chat, and admin accounts.

## Design

- Each endpoint requires `../config.php` and `../db.php`, checks `getDbConnection()`, and emits JSON through `sendJson()`. `requireAdminAuth()` gates every endpoint: it checks the session (`admin_logged_in`, `admin_id`), enforces `requireSameOrigin()` on non-GET requests, and re-reads the role from `admins` on every request (`currentAdminRole()`), destroying the session if the admin no longer exists. On GET it then releases the session lock (`session_write_close()`; `$_SESSION` stays readable), and slow POSTs release it before their SMTP/Gemini work (`applicants.php` rescreen/invite, `inquiries.php` reply), so the admin's parallel requests don't queue.
- Capabilities (`adminCapabilities()` in `config.php`, mirrored by `src/data/permissions.js`): `blogs`, `content`, `services`, `careers`, `applicants`, `chat`, `delete`, `users`, `listings` (superadmin/admin/editor), `inquiries` (superadmin/admin). Writes call `requireAdminCapability()`; deletes require `delete`; `users.php` is `requireSuperadmin()` end to end. GETs need only authentication, except `applicants.php`, `chat.php`, `inquiries.php` and `listings.php`, whose GETs also require their capability (candidate/visitor PII, Drive folder ids).
- `auth.php`: session check (also destroys sessions whose admin row vanished), login, and POST-only same-origin logout via `destroyAdminSession()`. Login is same-origin checked, type-checks inputs, throttles 5 failed attempts per IP and per email per 15 minutes (`rateLimit()` check-only, recorded on failure), verifies `password_verify()`, and calls `session_regenerate_id(true)` before storing identity/role. Login also bootstraps a superadmin: if none exists, the lowest-id (setup) account is promoted when it signs in. Self-service password change is two-step: `POST ?action=password-code` (verifies the current password, emails a single-use 6-digit code to `SECURITY_EMAIL`, 3 requests/15 min) then `POST ?action=password` (code valid 10 min, 5 tries, new password ≥10 chars, session regenerated).
- Endpoint/table mapping: `blogs.php` → `blog_posts`; `careers.php` → `job_openings`; `services.php` → `service_items`; `content.php` → `content_blocks`; `applicants.php` → `job_applicants` (+ `job_openings`, resume files, `lib/Ats.php`); `chat.php` → `chat_sessions` + `chat_messages` + `admins`; `users.php`/`auth.php` → `admins`; `listings.php` → `listing_overrides` + `data/listings.generated.json`/`listings.status.json` (via `lib/Listings.php`); `inquiries.php` → `inquiries` (filters; list pages of `limit` 1-200, default 50, continued by the last row's `before_at`/`before_id` or `offset`, rows without `meta.replies` (the `?id=` detail has them); status, delete, formula-safe UTF-8-BOM CSV export, `POST ?action=reply` emails the inquirer via `lib/EmailTemplate` and appends to `meta.replies`).
- Image uploads (`blogs.php`, `content.php`, `services.php`, `?action=upload_image`): 5 MB cap, `getimagesize()` MIME allowlist JPG/PNG/WebP, extension derived from MIME, random filename, saved under `webRootDir()/uploads/{blogs,content,services}`. All three use the shared `lib/upload-image.php` (`handleAdminImageUpload()`). Text fields are read with `inputText()` (array/object input → 422) and JSON bodies with `jsonBody()` (always an array). `services.php` also validates `kind` (service | product | package; an update without `kind` keeps the stored one). Property listings are not admin-managed: they come from the Google Drive via `api/cron/drive-sync.php`.
- PDO errors are logged with `error_log()` and returned as a generic message. Multi-column searches use distinct placeholders (`:search1..4`, `:s1..4`).

## Flow

1. The admin SPA authenticates via `/api/admin/auth.php`: GET or `?action=check` reports the session; POST logs in; `POST ?action=logout` clears it.
2. A resource request loads config/PDO, runs `requireAdminAuth()`, then capability checks per method before parsing JSON/form data and executing prepared INSERT/UPDATE/DELETE statements.
3. `blogs.php` lists every column except `content` with enterprise/status/category/search filters and pagination (`total`), returns one post with its body at `?id=`, creates with generated slug/publish timestamp, supports PUT/PATCH and hard delete. `careers.php` and `services.php` store list fields as JSON text. `content.php` upserts on `(page_slug, section_key)`. There is no admin listings endpoint (property listings come from the Drive sync). Public readers in `api/` serve these rows.
4. `applicants.php` calls `jobSchemaEnsure()` on every request; GET `?action=summary` returns only the status counts; the list returns the table's columns (`ats_details` cut to recommendation + summary) filtered by enterprise/status/job/`shortlisted`/search (LIKE-escaped), newest first or `sort=score` (unscored last), optionally paged (`limit` 1-200 with a `before_at`/`before_id`[/`before_score`] cursor or `offset`), plus `total` (filtered), `by_enterprise` and `summary`; `?id=` returns one applicant with full `ats_details`; `?action=resume` streams a validated resume; `?action=photo` streams the 2x2 photo (same capability, path confined to `uploads/photos`); `POST ?action=invite {id, interview_at: Y-m-d\TH:i (future), note?}` sets `interviewing` + schedule, clears `auto_rejected_at` and emails `atsSendInterviewInvite()` (`emailed` false if SMTP failed); the detail decodes `portfolio_links` to an array; `POST ?action=rescreen` (`applicants`, rate-limited 30/10 min per admin) re-runs `atsScreenSafely()` and returns the fresh `ats_*` fields; PUT updates status/notes; DELETE removes the resume, photo and row.
5. `chat.php` GET `?summary=1` returns the counts only; the session list takes `?status=open` (everything not closed) or one status (newest first, served by `idx_chat_status_updated`), `q` search (visitor name/email, enterprise, last message) and optional `limit` 1-200 + `offset` paging; `?session_id=` (+ `after_id`) returns a thread. It also claims waiting sessions, inserts admin replies, and closes conversations (closing note inserted before the status flips so the visitor's last poll can read it). Visitors see changes via `api/chat/poll.php`.
6. `users.php` lists safe account fields, hashes passwords, preserves at least one superadmin, prevents self-deletion, and never returns hashes.

## Integration

- Consumed by `src/routes/admin/*` managers; public endpoints in `api/` read the resulting blog, content, job, and service rows. Stored blog/content HTML is sanitized with DOMPurify when rendered in the admin previews.
- `config.php` owns session settings, auth/role/capability checks, same-origin and rate-limit helpers, and enterprise slug validation; `db.php` supplies PDO; `schema.sql` defines the tables.
- Role policy: editors write blogs/content/services; recruiters/admins/superadmins read and write careers/applicants/chat; deletes are admin/superadmin; only superadmins manage users.
- Resumes live under protected `uploads/resumes` (deny-all `.htaccess`) and are streamed only by `applicants.php`; ATS scoring and HR email come from `api/lib/Ats.php`.
